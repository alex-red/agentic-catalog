## Findings and best practices

### The supplied no-email example

Reviewed repository HEAD and artifact-path commit: `930d0b2cfabdc41feffb9f15ef0e981259d1e856`. Read **all seven tracked files**: README, MIT LICENSE, nested plugin manifest, tsconfig, hooks configuration, register module, and tests. [Pinned plugin subtree](https://github.com/AlexErrant/claude-code-no-email/tree/930d0b2cfabdc41feffb9f15ef0e981259d1e856/.claude/skills/no-email).

The [handler](https://github.com/AlexErrant/claude-code-no-email/blob/930d0b2cfabdc41feffb9f15ef0e981259d1e856/.claude/skills/no-email/hooks/register.ts) registers `prompt.context`, awaits the remaining middleware, then returns a copy whose `blocks` exclude the exact name `userEmail`. It preserves other result fields, block contents, and order. There are no filesystem, process, or network calls in the handler. Its two tests cover removing the block and leaving an email-free context unchanged; the tests were read, not run.

There is an important terminology correction: although the README calls this system-prompt removal, Anthropic's [published types](https://raw.githubusercontent.com/anthropics/claude-code/main/mods/types/claude-code.d.ts) describe `prompt.context` as context prepended to the **first user message**, and explicitly list `userEmail` among the engine's block names. This is removal from model-visible initial context, not necessarily editing the system-role message. The published declarations identify themselves as generated by 2.1.277 and warn that local generated types take precedence.

The source comment attributes the email to `oauthAccount.emailAddress` in `~/.claude.json` and says no setting disables it. That account-to-context path and the absence of a current setting were **not independently established** here. The README's claim about the model putting the email in request headers is author-reported, not reproduced evidence.

This is a **mod/function hook**, not a settings `PreToolUse` hook. Current [mods documentation](https://code.claude.com/docs/en/plugins/mods) distinguishes these mechanisms and says terminal mods are on by default from 2.1.287; Desktop has its own version. The actual plugin root is `.claude/skills/no-email/`, despite its directory name: it has a plugin manifest and no `SKILL.md`. Copying `register.ts` alone or treating the repository root as the plugin root would miss required packaging. The tsconfig refers to host-generated `.claude-plugin/types/tsconfig.json`, which is absent from the checkout; the host type-generation workflow is a development dependency.

**Limits inferred from the code:** it removes only the named block. It does not search file contents, Git identity, tool results, user messages, earlier transcripts, logs, or other plugins' stored data. An outer middleware handler could reinsert content after this handler returns. A new conversation is the appropriate validation target; installing it cannot retract data already transmitted.

Anthropic documents [mod failure behavior](https://code.claude.com/docs/en/plugins/mods/events#handle-a-hook-that-fails): without a custom error handler, failures before `next` skip the handler, while failures after `next` preserve the downstream result. This module has no `.catch` handler. Therefore, it should not be described as a fail-closed privacy guarantee. Validate loading, block shape, ordering with other mods, and the final request on each supported build.

### Choose the interception point by the intended effect

| Goal | Suitable point | Practical limit |
| --- | --- | --- |
| Keep personal data out of model input | Context/request transformation before inference | A display-only filter is too late; check all request kinds |
| Prevent a tool action | Synchronous pre-tool decision | A post-tool hook cannot undo an executed command |
| Normalize edited code | Post-edit formatter | Restrict to intended files and avoid recursive edit loops |
| Catch missed verification | Bounded completion gate | Continuation is not proof of correctness; keep CI authoritative |
| Preserve task state | Small session/compaction context hook | Repeated full-transcript injection adds cost and can replay stale instructions |
| Notify the user | Native notification event | Avoid forwarding prompts or code to external services by default |

These are research recommendations, not measured rankings. Use a rule for stable instruction, a skill for an on-demand procedure, and a hook when a specific lifecycle event must trigger executable behavior. Prefer a settings hook when it suffices; use a mod when the necessary structured event is unavailable there. Anthropic's [comparison](https://code.claude.com/docs/en/plugins/mods#compare-mods-settings-hooks-skills-and-mcp-servers) supports that distinction.

### Recommended engineering practices

The following are proposed catalog review criteria derived from the source inspection and failure cases, not a new mandatory repository policy:

1. **State a narrow guarantee.** Identify the exact event, fields, surfaces, and data paths covered. Distinguish input minimization, action blocking, output redaction, and logging controls.
2. **Keep guards synchronous and deterministic.** Do not delegate an exact path or secret policy to an LLM. Model-assisted reviews can provide advisory findings, with explicit cost and data handling.
3. **Make failures deliberate.** Exercise timeout, crash, missing runtime, invalid JSON and schema drift. A script's intended deny is irrelevant if the host treats its error as allow.
4. **Treat hook input as data.** Parse JSON, validate required fields, use process argument arrays, and never interpolate prompt/tool text into executable shell code. Resolve paths against the intended root and account for symlinks.
5. **Minimize scope and dependencies.** Narrow matchers; use installed tools with pinned dependencies. Do not download an installer or package on every tool call. Use explicit deadlines and small outputs.
6. **Make writes safe to repeat.** Format only intended paths; preserve unusual filenames; isolate state by session/worktree; account for concurrent hooks, edits, and branch changes.
7. **Bound continuation.** Honor retry state, avoid blocking read-only answers, and explain exactly which checks failed. Do not present a gate with an escape guard as a permanent completion guarantee.
8. **Test the composed host behavior.** Unit fixtures should include multiple/missing target blocks and preserved unrelated data. Integration fixtures should cover startup, resume, compaction, subagents, other mods, and final outgoing requests using synthetic identities.
9. **Keep sensitive values out of diagnostics.** Report block names/counts or categories instead of the removed email/secret. Review local logs and auxiliary model requests separately. Gemini's [best-practices guide](https://geminicli.com/docs/hooks/best-practices/) also warns that environment redaction is disabled by default; its overview's sanitized-environment wording should not be read as a blanket guarantee.
10. **Keep enforcement outside the agent where needed.** Repository CI, OS/filesystem permissions, scoped credentials and network controls remain separate controls. A regex hook should not be sold as comprehensive protection.
