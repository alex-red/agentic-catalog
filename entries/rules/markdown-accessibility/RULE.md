# Accessible Markdown documentation

When authoring or reviewing Markdown, check how readers understand and navigate the rendered document. Follow the project's renderer, documentation structure, and voice; keep edits within the requested scope.

- Make a link's purpose understandable from its label and nearby context. Where practical, let the label stand on its own in a screen reader's link list. Different destinations need distinguishable labels; preserve literal URLs when they are themselves the subject of an example.
- Describe an informative image's relevant meaning, including text needed to understand it. Keep purely decorative images skippable with an empty alternative. For a linked image, describe the destination or action. Give complex diagrams or charts an accompanying explanation. Inspect the image or ask for its purpose rather than inventing visual details.
- Use headings to express the document's hierarchy. Account for page titles generated by frontmatter or the renderer, and follow the project's top-level-heading convention. Use real headings for sections rather than bold styling alone; do not report a house preference as a universal accessibility requirement.
- Mark up sequences and groups as lists. Use tables for comparisons or data with clear headers, and explain relationships that a complicated table cannot express clearly in the renderer. Avoid using tables only to position text.
- Name interface controls and describe navigation in words. Color, location, shape, or icons can supplement an instruction but should not carry its only meaning. Keep essential information in text rather than relying on emphasis or emoji to communicate it.
- For embedded media, check for suitable captions, transcripts, and controls when relevant. Distinguish content issues from player or renderer behavior that requires runtime inspection.

Explain each reported barrier, who it affects, and a concrete correction. Mark uncertain image meaning or rendering behavior for verification. These checks support a documentation review; they do not establish accessibility conformance or replace testing with assistive technology.
